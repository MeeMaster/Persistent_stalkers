# Persistent Stalkers agent spec (branch `menu_load`: the main menu spike)

This branch, `menu_load`, is the second version of Persistent Stalkers, the main menu spike: the character is chosen at the main menu, before a game, and not in it (the MMO model, user's request, 2026-11-12). It was built the same day as a copy of this repo, `D:\Code\Stalker mods\PS_v2`, and then moved back here as this branch (user, 2026-11-12). `master` keeps the first version: the profile is chosen in a window opened in the game (see "Branches").

This file is the implementation spec. `README.md` is the player summary. If they disagree, this file wins on behavior, and the README should be updated to match.

## Branches

- **`master`**: the first version (2026-11-11). After a load whose save was not last played with the selected profile, an in-game window asks which character to play; a key opens it during play to switch. MCM has the profile controls and a Save mode dropdown with Off. Its own `AGENTS.md` and `README.md` describe it.
- **`menu_load`** (this branch): the main menu spike, described in this file. No profile window in the game, no profile controls in MCM: the main menu chooses, creates and removes profiles, and its own `ui_main_menu.script` replaces MCM's. MCM's Save mode is one checkbox, constant saves (no Off: None is chosen at the main menu). F8 switches in a game in debug mode only.
- Both install as the same mod, `D:\GAMMA\mods\Persistent_stalkers`, from whichever branch is checked out, and share the profile files: a profile made with one is read by the other.
- The character, the apply, timing, co-op and death are the same in both as of 2026-11-12; only choosing the profile differs. A fix to those parts made on one branch is not on the other until it is carried over. Which branch becomes the mod is open (see Open).

## What this is

A character profile for G.A.M.M.A. (Anomaly 1.5.3), solo and xrRazom co-op, like a character in an MMO: what the player carries and where (slots, belt), money, rank, reputation, needs, skills and recipes live in a file on the player's own machine, and travel with them into any world they play or join. Health, bleeding, body parts, radiation and psy health stay with the save.

It is its own mod, developed and installed on its own, like DANTE (`D:\Code\DANTE`) and Private Backrooms (`D:\Code\Private_backrooms`). It does not depend on either. It depends on Master Core (`D:\Code\Stalker mods\Master_core`) for the text form and files (`master_core_text`: the profile files and events), the xrRazom session and events (`master_core_net`), the profile list with create and remove (`master_core_profiles`, with the spec from `persistent_stalkers_profile.profile_spec()`), and the dev reload. A fix to those goes into Master Core (its `AGENTS.md`), not here. Without Master Core, `on_game_start` logs that it is not installed and the mod is off. GEM is not considered here (user's choice, 2026-10-21: GEM's own player profile, GEM `AGENTS.md`, is decided later).

Written 2026-10-21 from the design conversation (options A, B and C below); the main menu model 2026-11-12. Checked in fengari against a fake engine (see Checks). The main menu is not yet run in game.

## The design (decided 2026-10-21)

Two stores, the world save and the profiles, with items crossing between them (pickups, drops, trades, stashes, gifts). Loading an older save rolls back one store and not the other, so every crossing since that save is either doubled or lost. It cannot be fully reconciled. Two answers, both built, picked per machine in MCM: the checkbox `persistent_stalkers/constant_saves` ("Enable constant saves (Warning: may break the game)", last on the page) is A when ticked, B otherwise (user's request, 2026-11-12; until then a dropdown `persistent_stalkers/mode` with `off` as well, whose stored value is now ignored). `persistent_stalkers.chosen_mode()` gives MCM's choice, `mode()` the effective one (`off` for None).

- **A, "Character lives in the profile"** (`profile`, constant saves, the MMO model). The profile is written continuously; a save stores only the world. Every load or join makes the actor match the profile, whatever the save or xrRazom restored. Reloading never undoes anything for the character. Duplication on reload is accepted as "the world respawned". A crash loses at most the last few seconds of one player, and no world save is needed on leave, so save restrictions (YACS and the like) don't matter.
- **B, "Character follows the save"** (`save`, the default). The profile is written at each save. Loading a save takes that save's character. Solo behaves as usual. In co-op each client keeps a snapshot of its character per save key, which the host sends. Moving to another world still works (the profile is the last save's character), but loading an older save of the first world brings that save's character back.
- No `off` in MCM (removed 2026-11-12, user's request: redundant). Off is the **None** profile at the main menu: nothing read or written. So the mod is on as soon as it is installed: with no selection file, `default` is selected and adopts the first game's character. A player who wants nothing selects None.

Not built: **C** (A plus a host ledger of object ids taken by players, released on loading an older save). Kept in reserve if A's duplication matters in play.

Rejected: writing the profile on disconnect (one side of a transfer without the other: duplication or loss), and saving the world on every leave (overkill, and it fights save-restricting mods).

### Choosing the profile: the main menu (decided 2026-11-12)

The first version (branch `master`, 2026-11-11) chose the profile in a window opened in the game: after a load whose save was not last played with the selected profile, and with a key to switch during play. This branch replaces that with the MMO model (user's request, 2026-11-12): the character is chosen **at the main menu, before a game**, and every game started, loaded or joined from there is played with it. Changing it means quitting to the main menu. Still the user's earlier decisions: B ("on save") is the main mode; the loadout is drawn like a scaled-down inventory, not interactable.

- **The main menu** (`ui_main_menu.script`, our own; see "The main menu") shows the profile panel left to middle and the game's options on the right. The selected profile is shown when the menu opens; a click on a row selects (`persistent_stalkers_profile.choose`: `set_selected` with nothing pinned).
- **Arrival**: once the world has settled (Timing), no question. None: phase `none`, the save's character, nothing written. A profile: `target()` (B keeps the save's own character when the save was recorded with this profile, or the client's snapshot; otherwise the profile's file; A always the file).
- **A save from another profile, or from before the mod**, loaded with a profile selected gets that profile's character (B's rule from the start, now without the question). The save itself is untouched until the player saves over it.
- **An empty profile adopts** the character of the first game played with it: a new game's starting character, or a copy of a loaded save's character (how a playthrough branches now; the first version copied the character at the switch).
- **No switching in a game for players.** The pause menu (the same window) shows only the profile in use. **In debug mode** (the game started with `-dbg`, `DEV_DEBUG`; user's request, 2026-11-12) F8 opens the panel in a window of its own and switches (see "The main menu", the debug switch window). The console has the same switch, `persistent_stalkers.switch_to("name")`: the profile in use is written, then the new one's file replaces the actor (or an empty one adopts), and the selection follows.
- **Every host save still records what it was played with** (`m_data.persistent_stalkers.profile`: the profile, `none`, or nothing): B needs it to know a save is the profile's own. A client's `persistent_stalkers_worlds.txt` is still written at `pst_saved` but decides nothing now (`status()` shows it).
- MCM has no profile controls at all (user's request, 2026-11-12): creating and removing are the main menu's, removing with a warning box.

## Profiles

From Private Backrooms (`private_backrooms_rooms.script`, "Profiles"), lifted almost as it is (`persistent_stalkers_profile.script`):

- Named profiles, chosen at the main menu (above). The choice is remembered in `persistent_stalkers_selected.txt` (`{ profile }`, `set_selected` / `selected_profile`). Until 2026-11-11 it was MCM's `persistent_stalkers/active`; when the file is not there yet, that value is read once straight from `axr_options` (`axr_main.config:r_value("mcm", …)`: MCM's `ui_mcm.get` refuses a key with no option on the page). The choice is the machine's, not the save's, and not tied to the nickname. With none chosen, or a removed one, `default`.
- Files in `$app_data_root$` (`D:\Anomaly\appdata`): `persistent_stalkers_profile_<name>.txt` (the character), `persistent_stalkers_profile_<name>.saves.txt` (B's snapshots), `persistent_stalkers_profiles.txt` (the list, `default` implied), `persistent_stalkers_selected.txt` (the choice), `persistent_stalkers_worlds.txt` (a client's record of which profile each host save was played with). Names: letters, digits, `_`, `-`, up to 32.
- Text is a Lua-like table, written and read by the script's own encoder (no `loadstring`: the same reader takes events). Keys are sorted, so the same character always gives the same text, and a write is skipped when nothing changed. Numbers to 4 decimals; userdata (CTime) is dropped.
- No `os.remove` / `os.rename` in the engine: a write goes to `<file>.tmp`, then `<file>`; a load takes `<file>`, else `<file>.tmp`; an unreadable file is copied to `.bad`.
- **Shrink backups.** A write that leaves fewer than half of the items (of at least 6) first copies the old file to `.bak1` (`.bak2`, `.bak3` rotate). A wrong read, or a death with `death_strip`, can then be undone by hand.
- **Creating** writes an empty profile (`revision 0`, no `character`). An empty profile **adopts**: it takes the character of the first game played with it (a new game's starting character, or a copy of a loaded save's). A file of that name not on the list is listed as it is.
- **Removing** (the main menu's Remove profile, after a warning box): never `default` or None. The selected profile can be removed: `default` is selected first (Master Core never removes the profile in use), and selected back if the removal fails. Both files are copied to `…<name>.removed-<time>.txt` / `….saves.removed-<time>.txt` and emptied.
- **Getting a character back** (told in the warning box): create a new profile (any name, the removed one's too), select it and load a save played with the removed one (or join that game). The empty profile adopts that save's character: in A and in B with a new name through `target()`'s adopt; in B under the removed name the save names it, so the character follows the save, and the arrival writes it; a client adopts what xrRazom restored. What the profile gained after that save is only in the `.removed-` backup, put back by hand.
- **None** (user's request, 2026-10-21): the first row of the main menu's list, value `none`. No profile: the effective mode is `off`, nothing is read or written, and each save's own character is played (phase `none`). Saves made then are recorded as `none`. No file is ever made for it, and `none` cannot be created as a profile name (any case). `write()` refuses whenever the effective mode is `off`.
- **Only the main menu chooses.** MCM's list was limited to the main menu on 2026-10-21 (a pick there in a game replaced the character and, in A, overwrote the old profile, so a misclick could lose a character), and removed on 2026-11-11 with `set_profile`. The profile is pinned for the session on each map's first update (`persistent_stalkers_profile.pin`) and unpinned when the main menu is built without a game (`unpin`); in a game only `switch_to` (`use_profile`; debug F8 or the console) changes it.
- Tried and replaced in the first version: a "load this profile onto the current character" MCM button (2026-11-11), then the in-game profile menu with its arrival question and switch key (2026-11-11, still that repo's design).
- File: `{ version, revision, written, character }`; `revision` counts writes. Snapshots: `{ version, order = { newest key first }, by_key = { [key] = { character, t } } }`, 40 kept.

## The character

`persistent_stalkers_state.read()`:

- `items`: every carried item except **world items**, each `{ section, cond, uses, ammo, mag, ammo_type, addons, silencer, launcher, upgrades, parts, mag_data, mag_carried, slot, belt }` (Master Core's item record, `master_core_items.read`, plus where it sits; in grenade mode `grenades` replaces `mag` and `ammo_type`). World items (`is_world_item`): `quest_item` sections, DANTE's story-item patterns (`strelok`, `docuuments`, `intel`, `quest`, `notes`, `instruction`, `good_psy_helmet`, `bad_psy_helmet`), and `xrr_*`. The list is Master Core's (`master_core_world.is_story_item`, shared with DANTE). They belong to the world's tasks: never stored, never released or created.
- `slot`: `item_in_slot(1..13)` (G.A.M.M.A. `ui_inventory`: 1 knife, 2 pistol, 3 rifle, 4 grenade, 5 binoculars, 6 bolt, 7 outfit, 8 PDA, 9 detector, 10 torch, 11 artefact, 12 helmet, 13 backpack). `belt`: `item_on_belt(0..belt_count-1)`. `active`: `active_slot()`.
- `addons`: the packet's `addon_flags` bits (1 scope, 2 grenade launcher, 4 silencer), read from the game object (`weapon_*_status` 2: `weapon_is_scope` / `weapon_is_grenadelauncher` / `weapon_is_silencer`; otherwise the packet's bit). The server object's copy lags: a silencer screwed on was not stored (2026-10-27, as Private Backrooms 2026-10-26). `silencer` / `launcher`: the attached addon's item section (`silencer_name` / `grenade_launcher_name` through `utils_item.get_param`, so an upgrade's override counts). G.A.M.M.A. gives each weapon one silencer section. A created weapon whose addons differ once online (after the attach in step 2) is logged (`addons N, the profile has M`).
- `upgrades`: `iterate_installed_upgrades`, else the server packet (a client's mirror may list none live, DANTE probe). `parts`: the `parts` se var. `mag_data`: Mags Redux' `magazine_binder.get_data(id)` when that mod is loaded (it is disabled in the GEM profile; its data is keyed by object id, so a new item needs it moved: see Plan). `mag_carried`: the "ready" mark (`is_carried_mag`), set back with `toggle_carried_mag`.
- `money`, `rank`, `reputation`; `faction`: the true faction (`gameplay_disguise.get_default_comm()`, else the community without `actor_`).
- `goodwill`: each faction's community goodwill toward this player (`relation_registry.community_goodwill(faction, actor id)`), a map of faction name to a whole number, zeros included. Factions are `game_relations.factions_table`, else army, bandit, csky, dolg, ecolog, freedom, greh, isg, killer, monolith, renegade, stalker. This is the faction's attitude toward this one character. Faction-to-faction relations are the world's and are not stored. A profile written before this field has none: the first apply leaves the world's goodwill, and the next write stores it.
- `needs`: `satiety` (`cast_Actor():conditions():GetSatiety()`; the `satiety` property reads 1.0 per xrRazom), `thirst` (`actor_status_thirst.get_last_drink`), `sleep` (`actor_status_sleep.get_last_sleep`).
- Health is not stored. A profile used to keep `vitals` (`health`, `radiation`, `psy`, Body Health `limbs` / `timed`); that field is ignored. On an apply, `read_body()` memorizes the actor as the save or xrRazom left it: those vitals plus bleeding wounds (`conditions():WoundForEach`, one `{ bone, size }` per bone). After the gear is on, `apply_vitals` puts that back: wounds with `ClearWounds`, `AddWound(0, hit.wound, bone)`, `AddHit(size)` (xrRazom's restore; `AddWound` randomizes a non-zero size), limbs with `utils_obj.save_var` as DANTE does, `arszi_psy.set_psy_health`, radiation through `vital()`, then `set_health_ex`. A character written while bleeding out is not what the reload comes back as.
- `mod_state`: other mods' per-actor m_data, from the `MOD_STATE` list: each key names the module that owns it. Now only `skills_levels` (`haru_skills`). Read from the module's global when it keeps one, else `alife_storage_manager.get_state()` (the last save's). xrRazom's peer manifest (`xrr_peer_mdata.script`) lists more per-player keys; those that are world state (`visited_campfires`, garrison anger), keyed by object id (`carried_mags`), or campaign-timed (perk cooldowns) are left out on purpose. Add a key only with its owning module and a check that its `load_state` reads nothing else.
- `skill_tree`: Skill tree's character (own repo, `D:\Code\Stalker mods\Skill_tree`; `spec_core.get_state()`, saved there as `m_data.spec_skill_tree`), only when that mod is enabled (`spec_core` loaded): `class`, `perks` (each bought perk's paid record), `xp` and `total` (general and per class, unspent and ever earned), `craft2` (secondary craft), `respecs`, `version`, and any field it adds later. Left with the world: `xp_seen` / `xp_seq` (a peer's record of the host's task award numbers), `boosted` (artifact object ids), `rolled` (the host's anomaly rolls). Not a `MOD_STATE` entry: Skill tree's `load_state` is local. Without the mod nothing is read, nothing is set, and a write keeps the profile's stored `skill_tree` (`KEEP_WHEN_ABSENT` in the profile script), so playing a world without Skill tree does not lose it. Added 2026-11-11 (user's request).
- `talents`: Classes and Talents' character (xcvb, v0.56, needs the modded exes; `talents_functions` and `talents_leveling`), only when that mod is enabled. Its state is mostly script locals, so it is read by calling its own `save_state` into a fresh table and keeping the character's keys: `picked_class` (`"null"`: none), `talents_t` (talent name to level; zeros left out), `collector_var`, `monster_hunter_trophies` (by mutant kind), `merc_head_hunter_t` (by faction), and from `talents_leveling` `talent_levels` (each tree's `lvl`, `exp`, `points`, `spent_points`). Left with the world: cooldowns and durations (game-time tables) and the Kindred dogs (`kindred_*`: a squad in the world). Kept when absent (`KEEP_WHEN_ABSENT`), as `skill_tree`. Added 2026-11-12 (user's request).
- `recipes`: every `recipe_*` section whose note `encyclopedia__notes_<recipe>` is unlocked (`ui_pda_encyclopedia_tab.is_unlocked_note`; G.A.M.M.A.'s workshop counts a recipe as known that way).

### Making the actor match (`apply`)

Reconcile, not wipe. xrRazom's avatar and the actor stay; only what they carry changes (releasing the avatar made clients invisible, Private Backrooms `clearable`).

1. **Plan.** Carried items and stored ones are keyed by section, sorted upgrades and addon flags. Within a key, pairs go by nearest condition. Paired items are **kept** and get the stored condition, uses, ammo and magazine in place. Carried items left over are **released** (`alife_release_id`; a client can release what it carries, DANTE probe `test_release`; a host-owned id is refused and logged). Stored items left over are **created**: `alife_create_item(section, db.actor)`. On a client that is xrRazom's client spawn (`xrr_spawn_actor_item`), which returns the server object and is recorded by the host like quest rewards. Its Mags Redux data goes to the new id with `magazine_binder.set_data` right after `alife_create_item`, before it comes online: online, the binder makes default data for an id with none, and a magazine came back empty and a weapon with its default magazine (DANTE `move_tree`, 2026-10-30, as Mags Redux's `alife_clone_weapon`). On the host and in solo, a weapon's addon flags and ammo type go into its packet before it comes online. A stored section that no longer exists stays in the profile and is not created.
2. **Item state**, once each new item is online on this machine (DANTE probe method `full`): weapons unloaded, upgrades installed with `inventory_upgrades.force_upgrade` set, then `set_condition`, `set_remaining_uses`, `ammo_set_count`, or `unload_magazine` + `set_ammo_type` + `set_ammo_elapsed`; Mags Redux data with `set_data`. A new weapon that came online without a stored silencer or launcher (always on a client) gets that item created in the backpack and, once online, `weapon_addon_attach`ed, as G.A.M.M.A.'s silencer toggle does (`item_weapon.toggle_silencer`). 1 s later an addon item still there (the engine destroys it only on the server) is released; one that did not attach stays in the backpack, logged `did not attach`. `parts` 1 s later (writing it in the creation frame crashed DANTE). Direct setters, not `alife_process_item`: G.A.M.M.A.'s `Process_Item` applies only one of `uses` / `cond` / `ammo` per call. Items not online within 30 s are counted missing. Since 2026-11-04 all of this is Master Core's (`master_core_items.create` / `queue` with `attach`, `wait` 30 s and a `done` callback; `cancel` forgets the entries). The packet now also gets condition and upgrades (outside a session), and a weapon stored in grenade mode comes back in the normal mode with its grenades beside it.
3. **Placement**, 1.5 s later: stored-in-backpack items out of slots and off the belt, then slots in the order 7 (outfit: equipping one empties the belt and can push helmet and backpack out), 12, 13, then the rest (`move_to_slot(obj, slot, true)`), then the belt (`move_to_belt`). Checked 1 s later and redone once; what is still wrong is counted misplaced. Then `activate_slot(active)`.
4. **Stats**, each per MCM checkbox (items always): money (`give_money(difference)`), rank and reputation (`set_character_rank`, `set_character_reputation`), goodwill (`relation_registry.set_community_goodwill` for each stored faction; not `inc_faction_goodwill_to_actor`, which also shifts a random enemy and a random ally), faction (`gameplay_disguise.update_default(comm, true)`, else `set_character_community`; off by default), needs (`actor_status_thirst.load_state({drink = …})` and `actor_status_sleep.load_state({sleep = …})`, as Soulslike and xrRazom do; `change_satiety(difference)`), mod state (the owner's `load_state({[key] = value})`, then `after`: `haru_skills.on_game_load` recomputes skill bonuses), skill tree (the character's fields of `spec_core.get_state()` replaced in place, the world's kept, then `spec_core.migrate`, `spec_core.changed()`: effects re-applied and the perk summary sent to teammates; with no class, `notify("no_class")` opens the class picker; a perk id that Skill tree does not know is logged and left for its `load_state` to refund at the next load), talents (its `save_state` into a fresh table, the character's keys replaced; the effects of the class in play removed as its respec does, without releasing the coin or the dogs: `remove_all_items_weight`, `speed.remove_speed` / `weight.remove_weight` for every talent and `<class>_special`; then its two `load_state`s, which put the world's keys back unchanged, `recalc_all_items_weight`, and its window refreshed when open; its update adds the speed and weight modifiers again within a second), recipes (`unlock_note` for each one not yet known; known ones are never taken away). Then the memorized health (see above) is put back, after the outfit is equipped, so the save's health and bleeding land on the profile's gear.
   - Radiation: the actor's property setters may add (`CActor::Change*`) rather than set. `vital()` assigns the difference, reads back, and assigns the value if that did not land. Which one is true is unconfirmed. It is used only to put the save's radiation back.

The log gives `applying: N kept, N released (N refused), N created` and `applied: … missing, … misplaced, … recipes`, and a tip says the character is restored, with counts when something went wrong.

## Timing

- **Arrival** (each map's first update, `persistent_stalkers.script`): nothing is read or written until the world has settled. Host and solo: 3 s. Client: until `XrrNet():JoinSettling()` is false (xrRazom's gear restore; its own `kill_actor` waits on it), at most 90 s, plus 5 s, because xrRazom's `OnPeerConditionRestore` sets satiety, radiation and wounds again 1 and 3 s after its restore. In B a client also waits up to 20 s for the save's key (`WORLD_WAIT`): its snapshot is kept under it.
- **No question** (`decide()`): the profile was chosen at the main menu. None goes to phase `none`; a profile to `target()`. A tip names the profile played (`playing as …`, `character … restored`, or `playing without a profile`). The log names the profile and what the loaded world was last played with (`world_tag()`).
- **Which character** (`target()`):
  - A: the profile; an empty profile adopts.
  - B, host or solo: the save's own character when the save says it was last played with this profile (`m_data.persistent_stalkers.profile`). A save names the profile only when it is made while live (the world's character is the profile's), `none` while playing without one (phase `none`); before that (arriving, an apply) it keeps the loaded save's name, or nothing (`played_with()`). A new game's first autosave is made on `fake_start` before the arrival settles: it used to name the profile, and loading it followed the new game's starting kit instead of applying the profile (2026-11-11). Otherwise (new game, a save from before the mod, from another profile) the profile, as a client with no snapshot. An empty profile adopts.
  - B, client: the snapshot stored under the loaded save's key, else the profile, else adopt.
- Then the profile is written from the actor ("live"). Until then, and while dead, during a death rule's handling of a death (DANTE's return; Master Core's `master_core_world.death_busy()`, where DANTE registers), or during an apply, nothing is written. Whether another rule keeps the player alive through a death (DANTE, Azazel, Soulslike) is `master_core_world.death_rule()`; until 2026-11-04 this mod read `zzz_dante` and the two modes itself.
- **A writes** every 5 s when the character changed, 1 s after an item is taken, dropped, used, put in or taken from a box, or a menu closes (trade), at every host save, and on `on_level_changing`.
- **B writes** at every save: the host's `save_state`, and on a client the host's `pst_saved` (current character and a snapshot under that key). Also once on arrival (the loaded character).
- **Level change.** On `on_level_changing` a marker file (`persistent_stalkers_level_change.txt`: profile, mode, time) is written: Lua restarts on a client after a map change (DANTE). The next first update with a marker under 180 s old for the same profile and mode keeps the character as it is (no restore). Whether `on_level_changing` fires on an xrRazom client is untested: without it, a client's map change is a normal arrival, restored from a profile at most 5 s old (A).
- **MCM Apply** on constant saves: at once, mid-game too. Nothing is restored by it: the character in play stays, and only when the profile is written changes (ticked: from the next update on every change; unticked: at saves). A tip says which one is on. (Until 2026-11-12 the dropdown's Off stopped the mod mid-game; there is no Off now, None is chosen at the main menu.)

## Co-op (xrRazom)

- The mode and profile are each machine's: each player picks their own, for their own character.
- **Save keys.** The host (any mode, `off` included, so clients can use B) gives every save a key: `<session>-<counter>`, kept in the save (`m_data.persistent_stalkers = { session, counter, key, profile, mode }`). The session id is made at the first save of a world (time plus a random number) and the counter goes on from the loaded save. Every save sends `pst_saved {key}` to everyone. A client in arrival sends `pst_hello` to the host every 3 s until `pst_world {key}` answers (`""`: a new game, nothing saved).
- A client's `save_state` / `load_state` are xrRazom's surrogate (`xrr_peer_mdata_prime` / `apply`), not saves: ignored.
- What xrRazom already keeps per player in the host's save sidecar (`<save>.xrr_peers`, keyed by nickname): gear, money, rank, reputation, faction, satiety, thirst, sleep, radiation, wounds, actor pstor (Body Health limbs), and its peer m_data manifest (skills). In B, for a client who was in the loaded save, xrRazom's restore is already that save's character, so the reconcile keeps nearly everything.
- A host save made while a client is still restoring gives that client no snapshot (`host saved (<key>); not live here`). The next save does.

## Death

- DANTE active, Azazel, or Soulslike: nothing here; their rule keeps the player alive and the profile follows (A writes once DANTE's return is done).
- Otherwise (the game's death: death screen, reload), in A only: writing stops at `actor_on_before_death`, so the reload brings back the gear as it was just before death (the world rolls back). Health, bleeding, body parts, radiation and psy health are the save's, memorized when the save has loaded and put back after the profile's gear. MCM `death_strip` (off by default): the profile loses every carried item except what is equipped in slots 5, 8 and 10 (binoculars, PDA, torch, as DANTE keeps). A death cancelled after all (`flags.ret_value == false`, or the actor alive again) goes back to writing.
- B needs no rule: the reload's character is the save's.
